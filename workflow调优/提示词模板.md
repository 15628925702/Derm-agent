## Prompt Template

你现在在 `/data/gh/DermAgent` 项目中。

我要继续调一个已经完成大规模实验的单个 workflow。

目标 workflow：`{{MODEL}} / {{DATASET}}`

本轮目标不是“只要不变差”，而是尽量让该 workflow 在当前 frozen eval 原则下做到：

1. Agent Top-1 明确优于 baseline
2. Agent Top-k 明确优于 baseline
3. helped 要尽量多，hurt 必须严格受控
4. 不为了小样本刷分而引入不可解释的大范围 override

开始前必须先阅读并遵守：

- `workflow调优/调优执行规范.md`
- `workflow调优/调优顺序清单.md`

## 必须先做的追溯分析

不要直接改代码。先自动定位并阅读 `{{MODEL}} / {{DATASET}}` 已有的大规模产物：

1. 最新或目标大规模 compare report：
   - `paper_data/**/compare_reports/{{MODEL}}/{{DATASET}}/compare_agent_vs_qwen_*.json`
2. 对应 case-level export：
   - `paper_data/case_level_exports/*__{{MODEL}}__{{DATASET}}__*/`
3. baseline / full_dermagent summary
4. helped / hurt / unchanged cases
5. Top-k gain / Top-k hurt cases
6. workflow routing / profile / overrides：
   - `agent/model_workflow_router.py`
   - `agent/workflow_profiles.py`
   - 与 `{{MODEL}} / {{DATASET}}` 直接相关的 fusion、profile、skill、prompt 代码

先明确回答：

1. 当前 workflow 属于哪类问题：
   - Top-1 负向 / Top-k 正向
   - Top-1 持平 / Top-k 正向
   - Top-1 持平 / Top-k 持平
   - Top-1 弱正向
   - Top-1 与 Top-k 都强但还可继续挖
2. 当前 Top-1 与 Top-k 的 baseline / agent 数值是多少
3. helped / hurt / Top-k gain / Top-k hurt 各是多少
4. 主要掉点集中在哪些 label / disease category
5. 问题更像：
   - retrieval/evidence 没改善候选集
   - evidence 已改善 Top-k，但 final diagnosis/fusion 没转成 Top-1
   - override/保守策略过度推翻 baseline
   - uncertainty/contradiction 错误压制或错误放行

## 必须重点看的 case

至少分析：

1. 全部 hurt case；如果太多，先按 label 和混淆对分组，再抽最典型的 `10-20` 个
2. 全部 Top-k gain case；如果太多，先按混淆对分组，再抽最典型的 `10-20` 个
3. unchanged case 抽样 `10-20` 个
4. baseline 原本正确但 agent 改错的 case
5. agent differential 已包含正确答案但 final 没选中的 case

分析每个关键 case 时要看完整 evidence / final fusion 过程，包括：

- baseline final 与 differential
- agent initial perception
- selected skills
- selected evidence
- risk layer
- uncertainty / contradiction
- final diagnosis
- fusion decision / reasons

## 本轮优先考虑的修改方向

根据追溯结果选择最小且最相关的改动。优先考虑：

1. final diagnosis fusion
2. baseline anchored final / override gate
3. conservative fusion 程度
4. label-specific protection，例如 melanoma / malignant protection
5. Top-k-to-Top-1 promotion 的窄门规则
6. contradiction / uncertainty 压制强度
7. specialist evidence 对 final 的影响权重
8. evidence selection / skill priority
9. workflow profile / execution overrides

任何 promotion 或 override 都必须能解释：

- 为什么它会帮到目标混淆对
- 为什么不会伤害 baseline-correct case
- 它在已有 eval artifact 中命中了哪些 case
- 是否只是 memorized case，还是有可解释的 morphology / evidence 门槛

## 允许和不允许的改动

允许改：

- `{{MODEL}} / {{DATASET}}` 对应 workflow cell
- workflow profile / execution overrides
- skill 开关与优先级
- evidence selection
- final diagnosis / conservative fusion / override gate
- 与该 workflow 直接相关的 prompt 或 fusion 行为
- 针对该 workflow 的测试

不允许改：

- 大实验协议
- frozen evaluation 原则
- test split
- test writeback
- 数据划分
- 与该 workflow 无关的大面积重构
- 为了让指标好看而硬编码 ground truth 或 case id

## 验证节奏

每次验证必须用满 8 卡。

固定节奏：

1. small-case：`8` case
2. medium-case：`20` case
3. medium-case：`40` case
4. medium-case：`80` case
5. 先不要直接跑 `300`，除非前面稳定且用户明确同意

每一档都要汇总：

- Top-1 baseline / agent / delta
- Top-k baseline / agent / delta
- helped / hurt
- Top-k gain / Top-k hurt
- 关键 helped/hurt case id
- 是否和上一档是同一批 case
- 估计 300-case 上限是否可能只有少数 case

如果发现只是同一小撮 case 反复变好，要直接说明，不要夸大外推。

## 每轮结束必须做

1. 更新：
   - `workflow调优/调优顺序清单.md`
2. 运行相关单元测试
3. `git status` 检查只提交本 workflow 相关文件
4. git commit
5. 新建或更新分支：
   - `{{MODEL}}-{{DATASET}}-v2OK`
   - 如果 v2 已存在，则用当前合适版本号继续
6. 推到 GitHub
7. 停掉本轮启动的模型服务，释放 GPU

## 输出顺序

最终汇报必须按这个顺序：

1. 问题诊断
2. 本轮拟修改点
3. 实际代码修改了哪些文件
4. small / 20 / 40 / 80 验证结果
5. helped / hurt 模式
6. 是否只是固定少数 case 变好，以及对 300-case 的预期
7. commit hash、branch、push 状态
8. 是否建议进入下一轮
