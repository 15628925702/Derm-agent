# Workflow 调优执行规范 (2026-05-08)

这份文档是 `DermAgent` 单个 `model x dataset workflow` 定向调优的长期执行规范。

提示词模板见：

- `workflow调优/提示词模板.md`

模板只负责说明本轮目标 workflow；本文件负责规定分析、修改、验证、记录、git 的执行细节。

---

## 1. 总原则

### 1.1 一次只调一个 workflow

一次只调一个明确的 `model x dataset workflow cell`，不要混着动多个组合。

例子：

- `llama / isic2019`
- `medgemma / ham10000`
- `qwen / scin`

### 1.2 不改评测协议

调参时不允许：

- 改 frozen evaluation 原则
- 打开 test writeback
- 让 agent final 污染 test split
- 改 test split 或数据划分
- 改大实验协议来服务单个 workflow

允许改的是该 workflow 对应的策略、路由、证据选择、fusion、prompt 或 profile 行为。

### 1.3 目标是 Top-1 与 Top-k 都优于 baseline

阶段性目标不是“非负就行”，而是：

- Top-1 优于 baseline
- Top-k 优于 baseline
- helped 尽量多
- hurt 严格受控，优先追求 `hurt=0`

如果只提升 1 个 case，要明确说明收益偏弱，并继续寻找下一批可解释 residual。

### 1.4 先追溯，再修改

每轮必须先基于既有大规模产物做追溯分析，不允许凭印象改。

必须先弄清楚：

- 当前问题类型
- hurt 从哪里来
- Top-k gain 从哪里来
- evidence 是否已经改善候选集
- final/fusion 是否没吃进 evidence
- baseline anchor 或 override gate 是否过强/过弱

### 1.5 论文阶段允许先不重构，但必须隔离新增规则

当前阶段目标是先把论文所需 workflow 逐条调到优于 baseline。允许暂时继续在现有 fusion 框架里追加规则，不强制先重构 `conservative_fusion.py`。

但为了避免后面 workflow 的调优破坏前面已经调好的 workflow，所有新增 fusion / promotion / override / fallback 规则必须遵守：

- 每条新增规则必须强制绑定明确的 `workflow_cell_id`，不能只靠 model name、dataset name、label pair 或 profile 粗略判断。
- 尽量新增独立 helper 函数，例如 `_medgemma_isic_xxx_label()`，不要把新 workflow 逻辑塞进公共 helper。
- 不改公共 helper，除非已经证明该公共逻辑本身有 bug；如果必须改公共 helper，要说明影响范围，并补已有 OK workflow 的 regression case。
- 不改 `decide_conservative_agent_fusion()` 主干规则顺序，除非新规则无法通过更局部的 helper 或 route guard 接入。
- 每条规则都要有独立、可追溯的 reason string，不能复用含义不准确的旧 reason。
- 每条规则必须有单元测试，至少覆盖：
  - 目标 helped case 应触发
  - 相近但不满足条件的 case 不触发
  - baseline-correct / anchor case 不被误伤
- 每次调新 workflow 后，至少运行 `tests/test_conservative_fusion.py`，确认旧规则没有被新规则顺序或公共逻辑影响。


这是一条阶段性策略：先服务论文调优速度；论文所需 workflow 调完后，再考虑把 workflow-specific fusion rules 拆到独立目录和 registry。

## 2. 调参前必看产物

对于目标 workflow，先定位并阅读：

1. compare report
   - `paper_data/**/compare_reports/<model>/<dataset>/compare_agent_vs_qwen_*.json`
2. case-level export
   - `paper_data/case_level_exports/*__<model>__<dataset>__*/`
3. baseline summary 与 full_dermagent summary
4. helped / hurt / unchanged cases
5. Top-k gain / Top-k hurt cases
6. routing / profile / overrides
   - `agent/model_workflow_router.py`
   - `agent/workflow_profiles.py`
7. 直接相关代码
   - conservative fusion
   - final diagnosis prompt
   - dataset label space
   - skill selection / skill implementation
   - paper export / evaluation helper

如果存在多个候选 compare report，优先选择：

1. 用户明确指定的 report
2. 最新 frozen/eval300 report
3. 与当前 workflow branch/checklist 对应的 report

不要把不同 split、不同协议、不同 run mode 的结果混在一起比较。

## 3. 必须完成的追溯分析

### 3.1 判断问题类型

至少分类为：

1. `Top-1 负向 / Top-k 正向`
2. `Top-1 持平 / Top-k 正向`
3. `Top-1 持平 / Top-k 持平`
4. `Top-1 弱正向`
5. `Top-1 和 Top-k 都强但可继续挖 residual`

不同类型对应不同优先方向。

### 3.2 helped / hurt / unchanged

至少看：

- 全部 hurt case；如果太多，按 label 和混淆对分组后抽 `10-20` 个
- 全部 Top-k gain case；如果太多，按混淆对分组后抽 `10-20` 个
- unchanged case 抽样 `10-20` 个

重点回答：

1. agent 为什么能帮到
2. agent 为什么会误伤
3. 哪些 case evidence 明明对了，但 final 没吃进去
4. 哪些 case retrieval 变强，但最后仍跟 baseline 一样
5. 哪些 case baseline 本来正确，被 agent 过度推翻

### 3.3 区分 retrieval 问题与 final decision 问题

如果 Top-k 涨了但 Top-1 没涨，通常说明：

- evidence/retrieval 已经有帮助
- final diagnosis/fusion 没把帮助转成 Top-1

优先调：

- final fusion
- override gate
- conservative fusion 程度
- evidence 权重
- baseline-vs-evidence comparison

如果 Top-1 和 Top-k 都没动，通常说明：

- skill 没起作用
- retrieval 没召回有效证据
- workflow 路由几乎没真正介入

优先调：

- skill 开关
- planner / selection
- retrieval coverage
- workflow profile 触发方式

如果 Top-1 负向但 Top-k 仍涨，通常说明：

- 候选集比 baseline 更好
- final 输出过度干预或错误推翻

优先调：

- 推翻 baseline 的门槛
- override 触发条件
- contradiction / uncertainty 压制逻辑
- risk 分层后的 final output policy

### 3.4 按 label / disease category 看

必须按 label 看：

- 哪些类提升
- 哪些类下降
- 是否集中在少数混淆对
- 是否与 grouped/coarse taxonomy 映射有关

特别注意：

- melanoma / malignant label 是否保护不足
- `NV -> MEL`
- `NV -> SCC`
- `SCC -> AK`
- `SCC -> BCC`
- `BCC -> SCC`
- dataset-specific label space 是否匹配

### 3.5 检查 evidence package 质量

关键 case 要看：

- initial perception 是否稳定
- selected skills 是否合理
- selected evidence 是否相关
- risk layer 是否压错方向
- contradiction / uncertainty 是否过强或过弱
- final diagnosis prompt 是否被无关 evidence 挤占
- fusion decision reasons 是否符合预期

核心问题是：

- 证据包没找到对的证据
- 还是找到了但 final 没采纳

## 4. 可改内容和优先级

### 4.1 Skill 开关

可以改：

- 新增某个 skill
- 关闭某个 skill
- 只在某 dataset 打开某 skill
- 只在某 model/dataset 组合关闭某 skill

适用场景：

- evidence 太弱
- evidence 太乱
- 某 specialist 经常误导

### 4.2 Skill 优先级 / 权重

可以改：

- 某些 skill 更容易被选中
- 某些 skill 输出更容易进 selected evidence
- 某些 skill 在 final diagnosis 中占更大权重

适用场景：

- Top-k 已涨但 Top-1 没涨
- 正确信号被淹没
- 错误 specialist 话语权过高

### 4.3 Retrieval / evidence selection

可以改：

- 检索范围
- 检索数量
- specialist evidence 阈值
- prototype / confusion memory 权重
- exclusion evidence 权重

适用场景：

- workflow 完全没起效
- evidence 方向常偏
- retrieval 命中不稳定

### 4.4 Conservative fusion / override gate

可以改：

- agent 推翻 baseline 的门槛
- supporting vs opposing margin 阈值
- subtype override 阈值
- malignancy override 阈值
- evidence 不足时是否退回 baseline

适用场景：

- Top-1 负向但 Top-k 正向
- 明显是“会看了，但改错了”

这是最值得优先调的一层之一。

### 4.5 Uncertainty / contradiction

可以改：

- contradiction 触发敏感度
- uncertainty 对 final 的压制强度
- 低不确定时是否允许更积极 override
- 高不确定时是否更保守退回 baseline

适用场景：

- evidence 强却不敢改
- evidence 不稳却乱改

### 4.6 Risk layer / malignancy policy

可以改：

- risk flag 阈值
- malignancy evidence 优先级
- risk layer 是否压过 benign mimic
- final 输出是否过度受风险语言影响

适用场景：

- 恶性召回不理想
- 高风险类别被误判或不敢判

### 4.7 Final diagnosis prompt / final selection

可以改：

- final diagnosis 提示词重点
- baseline vs evidence 的显式比较方式
- final 是否必须贴合 selected evidence
- Top-k-to-Top-1 promotion 门槛

适用场景：

- Top-k 明显变好，但 Top-1 不涨

### 4.8 Dataset label-space / mapping

可以改：

- grouped label space
- dataset-specific label normalization
- coarse taxonomy / fine taxonomy 映射

适用场景：

- dataset 某些类总被映射错
- 某模型需要 grouped label space 才稳定

### 4.9 Workflow profile

可以改：

- workflow profile 选择
- skip_specialist_skills
- skip_experience_retrieval
- baseline_anchored_final
- sparse lesion reasoning
- coarse taxonomy workflow

适用场景：

- 某模型在该 dataset 上整体 reasoning style 不对
- 当前 profile 跟数据集特征不匹配

### 4.10 新增 workflow cell

如果旧 workflow 难以小改修好，可以新增 cell 并保留旧 cell 做 A/B。

推荐命名：

- `<model>__<dataset>__v2_conservative_final`
- `<model>__<dataset>__v2_evidence_promote`
- `<model>__<dataset>__v2_skill_rebalance`

## 5. Promotion / override 设计规范

任何 promotion 或 override 都要先做风险扫描。

必须回答：

1. 这条规则会命中哪些原始 eval case
2. 命中的 case 中 baseline-correct 有多少
3. 命中的 case 中 GT 分布是什么
4. 是否集中在同一 morphology / location / evidence pattern
5. 是否需要 label-specific protection
6. 是否可能只是 case-id memorization

禁止：

- 用 case id 作为规则条件
- 用 ground truth 作为规则条件
- 为了一个 case 放开大范围 label promotion
- 未扫描 baseline-correct 风险就放宽 override

优先选择：

- label pair 明确
- morphology 明确
- location 明确
- uncertainty 明确
- selected evidence present
- support margin / subtype margin 有边界
- full artifact 扫描命中低风险

## 6. 验证节奏

每次验证必须用满 8 卡。

固定节奏：

1. `8` case
2. `20` case
3. `40` case
4. `80` case
5. 不直接跑 `300`，除非前面稳定且用户同意

每一档都要统计：

- Top-1 baseline / agent / delta
- Top-k baseline / agent / delta
- helped / hurt
- Top-k gain / Top-k hurt
- label-level变化
- 关键 helped/hurt case id

如果 targeted mix 里 helped 是同一批 case，必须明确说明：

- small/20/40/80 的新增 helped 是否重复
- 300-case 可能最多只多几个
- 是否需要下一轮寻找新的 residual

---

## 7. 8 卡使用规范

允许：

1. 同一 workflow 分 shard 并行
2. 同一 workflow 多个 candidate 并行
3. small / medium 多组并行

不推荐：

- 单卡串行、其他 GPU 空着
- 已经确定要验证却长时间闲置 GPU

每轮结束后必须停掉本轮启动的模型服务，并确认 GPU 已释放。

---

## 8. 每轮记录规范

每轮结束都要更新：

- `workflow调优/调优顺序清单.md`

记录内容至少包括：

- 日期
- workflow
- 版本名
- 原始大规模 baseline / agent 指标
- 问题诊断
- 修改点
- small / 20 / 40 / 80 结果
- helped / hurt / Top-k gain / Top-k hurt
- 关键 case id
- 是否只是同一批 case 变好
- 下一轮方向

## 9. Git 与分支规范

### 9.1 分支命名

按这个格式：

- `<model>-<dataset>-v2OK`
- `<model>-<dataset>-v3OK`
- `<model>-<dataset>-v4OK`

例子：

- `llama-isic2019-v2OK`
- `medgemma-ham10000-v2OK`
- `qwen-scin-v3OK`

### 9.2 提交流程

每次阶段完成后：

1. `git status` 确认改动范围
2. 只 stage 本 workflow 相关代码、测试、checklist
3. commit message 写清楚
4. push 到对应 GitHub 分支

commit message 示例：

- `Tune llama isic2019 workflow`
- `Adjust medgemma ham10000 evidence fusion`
- `Expand qwen scin workflow promotions`

### 9.3 不要做

- 不要把多个 workflow 混在一个分支里调
- 不要提交无关运行产物
- 不要把用户未要求提交的 dirty file 混进 commit
- 不要调完不 commit
- 不要跑完有结果但代码状态不可回溯

最终汇报建议包含：

- hurt 模式
