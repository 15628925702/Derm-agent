# Workflow 调优执行规范 (2026-05-08)

这份文档是 `DermAgent` 单个 `model x dataset workflow` 定向调优的长期执行规范。

提示词模板见：

- `workflow调优/提示词模板.md`

模板只负责说明本轮目标 workflow；本文件负责规定分析、修改、验证、记录、git 的执行细节。

---

## 1. 总原则

### 1.1 一次只调一个 workflow

一次只调一个明确的 `model x dataset workflow cell`，不要混着动多个组合。

例子：

- `llama / isic2019`
- `medgemma / ham10000`
- `qwen / scin`

### 1.1.1 多对话同步调优隔离规范

如果为了效率在多个对话里并行调多个 workflow，必须把“每个对话一次只调一个 workflow”升级为硬隔离规则：

- 每个对话必须在开头声明唯一目标 workflow，例如 `medgemma / ham10000`，本对话全程不得顺手分析、修改、验证或提交其它 workflow。
- 每个对话必须使用独立 git branch，分支名建议为 `tune-<model>-<dataset>` 或 `<model>-<dataset>-v2OK`；不得让多个对话同时在同一工作分支上改代码。
- 每个对话必须使用独立 run tag / output tag，建议格式为 `<model>__<dataset>__<YYYYMMDD>__<dialog_id>`；验证产物不得写入其它 workflow 的 run 目录。
- 每个对话必须使用独立 GPU / port 段，或由用户显式调度验证队列；不得在不知道其它对话占用情况时启动模型服务抢同一组端口。
- 每个对话提交前必须运行 `git status --short` 与 `git diff --stat`，确认 staged/commit 范围只包含本 workflow 相关代码、测试、清单记录和本 workflow 验证产物。
- 如果多个对话都需要修改 `skills/workflow_fusion_decision.py`，每个对话只能新增或修改自己目标 `workflow_cell_id` 对应的 helper、reason、route guard 豁免和测试；不得整理、移动或重排其它 workflow 规则。
- 如果多个对话都需要修改 `tests/test_conservative_fusion.py`，每个对话只能追加自己 workflow 的测试 helper / case；不得删除、重命名或批量改写其它 workflow 的测试。
- 如果多个对话都需要更新 `workflow调优/调优顺序清单.md`，只能追加或更新自己 workflow 的 tuning log 与状态行；不得重排其它对话刚写入的日志。若出现冲突，最后由合并对话统一整理。
- 不允许在一个 workflow 的分支里“顺手修”另一个 workflow 的规则，即使看起来明显有问题；必须记录为下一条候选，另开对话或另开分支处理。

同步调优推荐节奏：

1. 三个对话先并行完成全量 case-level 追溯分析和规则候选设计。
2. GPU 验证不要无序并发；如果只有一套 8 卡，按队列轮流跑 `8 -> 20`，先比较收益。
3. 只有 `20-case` 已经显示 `hurt=0` 且收益不是固定单个 case 时，再安排该 workflow 继续跑 `40 -> 80`。
4. 每个对话结束时必须停止自己启动的模型服务，并在最终汇报里写清 GPU / port 是否释放。

同步调优的最终合并必须在一个专门合并对话或合并分支中完成。合并者要逐个 cherry-pick 或 merge 三条 workflow 分支，逐个解决 `skills/workflow_fusion_decision.py` 与 `tests/test_conservative_fusion.py` 冲突，重新运行 `tests/test_conservative_fusion.py`，并确认每条 workflow-specific 规则仍然只绑定自己的 `workflow_cell_id`。

### 1.2 不改评测协议

调参时不允许：

- 改 frozen evaluation 原则
- 打开 test writeback
- 让 agent final 污染 test split
- 改 test split 或数据划分
- 改大实验协议来服务单个 workflow

允许改的是该 workflow 对应的策略、路由、证据选择、fusion、prompt 或 profile 行为。

### 1.3 目标是 Top-1 与 Top-k 都优于 baseline

阶段性目标不是“非负就行”，而是：

- Top-1 优于 baseline
- Top-k 优于 baseline
- helped 尽量多
- hurt 严格受控，优先追求 `hurt=0`

如果只提升 1 个 case，要明确说明收益偏弱，并继续寻找下一批可解释 residual。

### 1.4 先追溯，再修改

每轮必须先基于既有大规模产物做追溯分析，不允许凭印象改。

必须先弄清楚：

- 当前问题类型
- hurt 从哪里来
- Top-k gain 从哪里来
- evidence 是否已经改善候选集
- final/fusion 是否没吃进 evidence
- baseline anchor 或 override gate 是否过强/过弱

新增或放宽规则前，必须优先看完整大规模 case-level 分布，而不是只看前几个 small/medium 窗口里的 helped case。尤其要先统计和分组：

- 全部 `agent_topk_hit=true` 但 `agent_correct=false` 的 case，也就是正确答案已经进 differential / Top-k，但 final diagnosis 没选中的 case
- 全部 baseline Top-1 正确但 agent 改错的 case
- 全部 Top-k gain 与 Top-k hurt case
- 全部与目标 promotion label pair 相同或相近的 baseline-correct case

这是执行顺序硬约束：先完成全范围 case-level 分布分析，再写或放宽规则。不能先根据前面窗口里的少数 case 写规则，再用后续大样本验证去碰运气。

如果存在 eval300 或同等级全量 frozen 产物，调优分析必须以全量产物为主；small/20/40/80 只用于验证节奏和快速回归，不得替代全量错误池分析。若暂时没有全量产物，必须在进入较大修改前明确说明当前规则只来自局部窗口，且需要后续全量验证。

如果某条规则只在一个局部 offset 窗口有效，而在补充窗口或全量 300 中没有继续贡献，必须明确说明收益会被大数据量稀释，不得把局部小样本收益包装成全局明显优于。遇到这种情况，应回到全量 case-level 分布，优先分析所有 Top-k 已包含正确答案但 Top-1 选错的 case，而不是继续围绕早期 helped case 加条件。

### 1.4.1 大规模 case 也必须能提高

后续调 workflow 不能只为了前面窗口的一两个 case 反复加规则。除非是在修复明确的 `hurt` 或严重安全负向，否则新增 promotion / override 的默认目标必须是：在 eval300 或同等级全量产物上形成可见的分布式收益。

新增规则前必须做一次“全量候选扫描”，至少包括：

- 在完整 case-level records 上模拟候选谓词，统计命中总数、预计 helped、预计 hurt、预计 Top-k gain、预计 Top-k hurt。
- 按 `label / anatom_site / baseline final -> agent final / evidence marker / support_margin / uncertainty` 分组，确认规则不是只记住单个 case id。
- 同时扫描相同或相近 predicate 下的 baseline-correct case；若会命中 baseline-correct，必须先加阻断条件或放弃。
- 对 Top-k 目标，不能只看 `agent_topk_hit=true` 的 case；还必须看 baseline/agent 都 Top-k miss 但 evidence 有稳定正确标签信号的 case，因为这类才可能带来新的 Top-k gain。

规则收益判断按以下优先级执行：

1. 优先选择能在全量 300 中贡献多个 helped / Top-k gain，且 `hurt=0`、`Top-k hurt=0` 的窄门规则。
2. 如果规则只提升 `1-2` 个 case，默认视为弱收益；只有在它修复明确 hurt、保护 malignant safety、或是更大 pattern 的必要组成部分时才允许保留，并必须在记录中写明“收益偏小”。
3. 如果 small/20/40/80 表现好但 eval300 收益只剩一小撮 case，必须继续回到全量 residual 池找下一批可解释 pattern，不能把小窗口收益当成本轮结束依据。
4. 如果 Top-1 已明显提高但 Top-k 仍弱，要优先寻找 evidence-only 或 differential-expansion 的窄门 Top-k gain 规则，而不是继续放宽会伤 baseline-correct 的 Top-1 override。

最终汇报必须明确说明：本轮收益是分布在多个 case / label / pattern 上，还是主要来自固定少数 case；若主要来自少数 case，必须建议继续调优或降低对 300-case 外推的表述强度。

### 1.5 Workflow fusion 规则必须放在 fusion experience memory 层

从 `fusion-experience-memory-migration` 之后，workflow-specific final fusion / promotion / override / fallback 逻辑的主入口是：

- `memory/fusion_experience/workflow_fusion_decision.py`

`skills/workflow_fusion_decision.py` 只保留旧 import 兼容 wrapper；`agent/conservative_fusion.py` 只保留 agent 侧兼容 wrapper，不再作为新增 workflow 规则的实现位置。`agent/run_agent.py` 运行时应直接使用 memory 层 fusion。后续调优时，如果需要新增或修改 fusion 规则，默认改 `memory/fusion_experience/workflow_fusion_decision.py`，不要把新逻辑写回 `skills/` 或 `agent/conservative_fusion.py`。

这样做是为了把数据集 / workflow 混淆经验归入可审计的经验记忆层，避免把经验沉淀误归类为通用 skill；也避免出现“关了经验库但效果仍由 agent fusion 暗中完成”的问题。

Fusion experience accumulation 是 proposal-first 机制，默认必须关闭。只有显式设置 `DERMAGENT_ENABLE_FUSION_EXPERIENCE_ACCUMULATION=1` 时，运行时才允许在 `memory/fusion_experience/proposals/` 追加 pending observation；这些 observation 没有运行时效果，必须经人工审核、补测试、验证后才能写入正式规则。

但为了避免后面 workflow 的调优破坏前面已经调好的 workflow，所有新增 fusion / promotion / override / fallback 规则必须遵守：

- 每条新增规则必须强制绑定明确的 `workflow_cell_id`，不能只靠 model name、dataset name、label pair 或 profile 粗略判断。
- `workflow_cell_id` 必须是唯一生效边界：同一个 model、同一个 dataset、同一个 profile，甚至同一个 model+dataset 的其他 workflow cell，都不能被当前 workflow 的规则命中。不得用 `model_workflow_profile`、`dataset_name`、`model_name` 作为 workflow-specific 规则的兜底入口。
- 尽量新增独立 helper 函数，例如 `_medgemma_isic_xxx_label()`，不要把新 workflow 逻辑塞进公共 helper。
- 不改公共 helper，除非已经证明该公共逻辑本身有 bug；如果必须改公共 helper，要说明影响范围，并补已有 OK workflow 的 regression case。
- 不改 `decide_conservative_agent_fusion()` 主干规则顺序，除非新规则无法通过更局部的 helper 或 route guard 接入。
- 每条规则都要有独立、可追溯的 reason string，不能复用含义不准确的旧 reason。
- 每条规则必须有单元测试，至少覆盖：
  - 目标 helped case 应触发
  - 相近但不满足条件的 case 不触发
  - baseline-correct / anchor case 不被误伤
- 每次调新 workflow 后，至少运行 `tests/test_conservative_fusion.py`，确认旧规则没有被新规则顺序或公共逻辑影响。

如果本轮目标是验证迁移或重构，而不是新增规则，必须额外做旧实现与新 skill 的逐 case 决策等价校验；推荐在多个 model/dataset live 或 frozen report 上对比 old/new `decide_conservative_agent_fusion()` 输出，要求 `mismatch=0` 后再宣称复刻成功。

当前仍允许把所有 workflow-specific fusion 规则集中在这一个 memory 文件里，后续再按用户要求细分 approved rules 或 registry。不要在没有必要时提前拆成很多文件。

## 3. 必须完成的追溯分析

### 3.1 判断问题类型

至少分类为：

1. `Top-1 负向 / Top-k 正向`
2. `Top-1 持平 / Top-k 正向`
3. `Top-1 持平 / Top-k 持平`
4. `Top-1 弱正向`
5. `Top-1 和 Top-k 都强但可继续挖 residual`

不同类型对应不同优先方向。

### 3.2 helped / hurt / unchanged

至少看：

- 全部 hurt case；如果太多，按 label 和混淆对分组后抽 `10-20` 个
- 全部 Top-k gain case；如果太多，按混淆对分组后抽 `10-20` 个
- unchanged case 抽样 `10-20` 个
- 全部 Top-k 对但 Top-1 错的 case：`agent_topk_hit=true` 且 `agent_correct=false`
- 全部 baseline-correct 但 agent final 改错的 case：`baseline_correct=true` 且 `agent_correct=false`

重点回答：

1. agent 为什么能帮到
2. agent 为什么会误伤
3. 哪些 case evidence 明明对了，但 final 没吃进去
4. 哪些 case retrieval 变强，但最后仍跟 baseline 一样
5. 哪些 case baseline 本来正确，被 agent 过度推翻

设计 Top-k-to-Top-1 promotion 时，必须先把所有 `agent_topk_hit=true && agent_correct=false` 的 case 按 `ground_truth / baseline final / agent final / agent differential / site / evidence marker / fusion reason` 分组，再从高频、可解释、低 baseline-correct 风险的组里选规则。不能只根据一两个已知 helped case 反推条件；如果同一条件同时命中大量 baseline-correct case，必须先加阻断或放弃该规则。

每条 Top-k-to-Top-1 promotion 的分析记录里必须说明：

- 它在全量 case-level 里命中的全部 case 数
- 其中预计 helped / hurt / 不改变 Top-1 的数量
- 它覆盖的 Top-k 对但 Top-1 错 case 是否来自多个 offset 区间，而不是同一小段反复出现
- 它没有误伤 baseline-correct case 的证据，或明确的阻断条件
- 如果 300-case 上只可能多出少数 case，必须如实写成“小幅收益”，不能描述成明显全局提升

### 3.3 区分 retrieval 问题与 final decision 问题

如果 Top-k 涨了但 Top-1 没涨，通常说明：

- evidence/retrieval 已经有帮助
- final diagnosis/fusion 没把帮助转成 Top-1

优先调：

- workflow fusion skill
- override gate
- baseline anchor / conservative fallback 程度
- evidence 权重
- baseline-vs-evidence comparison

如果 Top-1 和 Top-k 都没动，通常说明：

- skill 没起作用
- retrieval 没召回有效证据
- workflow 路由几乎没真正介入

优先调：

- skill 开关
- planner / selection
- retrieval coverage
- workflow profile 触发方式

如果 Top-1 负向但 Top-k 仍涨，通常说明：

- 候选集比 baseline 更好
- final 输出过度干预或错误推翻

优先调：

- 推翻 baseline 的门槛
- override 触发条件
- contradiction / uncertainty 压制逻辑
- risk 分层后的 final output policy

### 3.4 按 label / disease category 看

必须按 label 看：

- 哪些类提升
- 哪些类下降
- 是否集中在少数混淆对
- 是否与 grouped/coarse taxonomy 映射有关

特别注意：

- melanoma / malignant label 是否保护不足
- `NV -> MEL`
- `NV -> SCC`
- `SCC -> AK`
- `SCC -> BCC`
- `BCC -> SCC`
- dataset-specific label space 是否匹配

### 3.5 检查 evidence package 质量

关键 case 要看：

- initial perception 是否稳定
- selected skills 是否合理
- selected evidence 是否相关
- risk layer 是否压错方向
- contradiction / uncertainty 是否过强或过弱
- final diagnosis prompt 是否被无关 evidence 挤占
- fusion decision reasons 是否符合预期

核心问题是：

- 证据包没找到对的证据
- 还是找到了但 final 没采纳

## 4. 可改内容和优先级

### 4.1 Skill 开关

可以改：

- 新增某个 skill
- 关闭某个 skill
- 只在某 dataset 打开某 skill
- 只在某 model/dataset 组合关闭某 skill

适用场景：

- evidence 太弱
- evidence 太乱
- 某 specialist 经常误导

### 4.2 Skill 优先级 / 权重

可以改：

- 某些 skill 更容易被选中
- 某些 skill 输出更容易进 selected evidence
- 某些 skill 在 final diagnosis 中占更大权重

适用场景：

- Top-k 已涨但 Top-1 没涨
- 正确信号被淹没
- 错误 specialist 话语权过高

### 4.3 Retrieval / evidence selection

可以改：

- 检索范围
- 检索数量
- specialist evidence 阈值
- prototype / confusion memory 权重
- exclusion evidence 权重

适用场景：

- workflow 完全没起效
- evidence 方向常偏
- retrieval 命中不稳定

### 4.4 Workflow fusion skill / override gate

可以改：

- agent 推翻 baseline 的门槛
- supporting vs opposing margin 阈值
- subtype override 阈值
- malignancy override 阈值
- evidence 不足时是否退回 baseline

适用场景：

- Top-1 负向但 Top-k 正向
- 明显是“会看了，但改错了”

这是最值得优先调的一层之一。

实现位置要求：

- 新增 workflow-specific final fusion / promotion / override / fallback 规则：改 `memory/fusion_experience/workflow_fusion_decision.py`
- 保持 `agent/conservative_fusion.py` 为兼容 wrapper；除非 wrapper 本身坏了，否则不要在这里新增规则
- 每条规则必须在 `fusion_decision["reasons"]` 中写入独立、可追溯 reason string
- 每条规则必须精确绑定 `workflow_cell_id`
- 单元测试继续写在 `tests/test_conservative_fusion.py`，因为它测试的是 fusion 行为契约，不是文件名

### 4.5 Uncertainty / contradiction

可以改：

- contradiction 触发敏感度
- uncertainty 对 final 的压制强度
- 低不确定时是否允许更积极 override
- 高不确定时是否更保守退回 baseline

适用场景：

- evidence 强却不敢改
- evidence 不稳却乱改

### 4.6 Risk layer / malignancy policy

可以改：

- risk flag 阈值
- malignancy evidence 优先级
- risk layer 是否压过 benign mimic
- final 输出是否过度受风险语言影响

适用场景：

- 恶性召回不理想
- 高风险类别被误判或不敢判

### 4.7 Final diagnosis prompt / final selection

可以改：

- final diagnosis 提示词重点
- baseline vs evidence 的显式比较方式
- final 是否必须贴合 selected evidence
- Top-k-to-Top-1 promotion 门槛

适用场景：

- Top-k 明显变好，但 Top-1 不涨

### 4.8 Dataset label-space / mapping

可以改：

- grouped label space
- dataset-specific label normalization
- coarse taxonomy / fine taxonomy 映射

适用场景：

- dataset 某些类总被映射错
- 某模型需要 grouped label space 才稳定

### 4.9 Workflow profile

可以改：

- workflow profile 选择
- skip_specialist_skills
- skip_experience_retrieval
- baseline_anchored_final
- sparse lesion reasoning
- coarse taxonomy workflow

适用场景：

- 某模型在该 dataset 上整体 reasoning style 不对
- 当前 profile 跟数据集特征不匹配

### 4.10 新增 workflow cell

如果旧 workflow 难以小改修好，可以新增 cell 并保留旧 cell 做 A/B。

推荐命名：

- `<model>__<dataset>__v2_conservative_final`
- `<model>__<dataset>__v2_evidence_promote`
- `<model>__<dataset>__v2_skill_rebalance`

## 5. Promotion / override 设计规范

任何 promotion 或 override 都要先做风险扫描。

必须回答：

1. 这条规则会命中哪些原始 eval case
2. 命中的 case 中 baseline-correct 有多少
3. 命中的 case 中 GT 分布是什么
4. 是否集中在同一 morphology / location / evidence pattern
5. 是否需要 label-specific protection
6. 是否可能只是 case-id memorization

禁止：

- 用 case id 作为规则条件
- 用 ground truth 作为规则条件
- 为了一个 case 放开大范围 label promotion
- 未扫描 baseline-correct 风险就放宽 override

优先选择：

- label pair 明确
- morphology 明确
- location 明确
- uncertainty 明确
- selected evidence present
- support margin / subtype margin 有边界
- full artifact 扫描命中低风险

## 6. 验证节奏

每次验证必须用满 8 卡。

固定节奏：

1. `8` case
2. `20` case
3. `40` case
4. `80` case
5. 不直接跑 `300`，除非前面稳定且用户同意

每一档都要统计：

- Top-1 baseline / agent / delta
- Top-k baseline / agent / delta
- helped / hurt
- Top-k gain / Top-k hurt
- label-level变化
- 关键 helped/hurt case id

如果 targeted mix 里 helped 是同一批 case，必须明确说明：

- small/20/40/80 的新增 helped 是否重复
- 300-case 可能最多只多几个
- 是否需要下一轮寻找新的 residual

## 7. 8 卡使用规范

允许：

1. 同一 workflow 分 shard 并行
2. 同一 workflow 多个 candidate 并行
3. small / medium 多组并行

不推荐：

- 单卡串行、其他 GPU 空着
- 已经确定要验证却长时间闲置 GPU

每轮结束后必须停掉本轮启动的模型服务，并确认 GPU 已释放。

## 9. Git 与分支规范

### 9.1 分支命名

按这个格式：

- `<model>-<dataset>-v2OK`
- `<model>-<dataset>-v3OK`
- `<model>-<dataset>-v4OK`

例子：

- `llama-isic2019-v2OK`
- `medgemma-ham10000-v2OK`
- `qwen-scin-v3OK`

### 9.2 提交流程

每次阶段完成后：

1. `git status` 确认改动范围
2. 只 stage 本 workflow 相关代码、测试、checklist
3. commit message 写清楚
4. push 到对应 GitHub 分支

commit message 示例：

- `Tune llama isic2019 workflow`
- `Adjust medgemma ham10000 evidence fusion`
- `Expand qwen scin workflow promotions`

### 9.3 不要做

- 不要把多个 workflow 混在一个分支里调
- 不要提交无关运行产物
- 不要把用户未要求提交的 dirty file 混进 commit
- 不要调完不 commit
- 不要跑完有结果但代码状态不可回溯
